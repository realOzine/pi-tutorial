LESSON 01 / 从请求到反馈

最小 Agent 循环

模型可以提出“读取 README.md”，但这句话本身不会打开文件。需要一段程序执行工具、记录结果，再把新的消息历史发给模型。这段程序，就是我们这一课要实现的循环。

产出：可测试的 runAgentLoop前提：函数、数组、条件与循环模型与文件：均为模拟

01从一个任务开始

假设你接手一个项目，想知道怎样启动它。你给 Agent 的任务是：

请读取 README.md，告诉我怎样启动这个项目。

在这个教学场景中，README 的内容是 启动命令：npm run dev。模型起初只收到用户的问题，并没有这段文件内容。因此，程序需要完成三件事：接住模型提出的读取请求，执行读取，再把读取结果交回去。

完成本课后，你应该能从一段消息历史判断程序走到了哪里；实现“有工具请求就执行并继续、没有工具请求就结束”的控制流；解释工具失败和预算耗尽为什么是两种不同的结果。

来自 Go：先读懂这里用到的 TypeScript

Promise<T> 表示一个稍后得到 T 的异步结果。await model(messages) 会等待这次调用结束；它不会自动再调用一次。下一次模型请求仍由你写的循环触发。

每条消息都有 role，值为 user、assistant 或 tool。TypeScript 的联合类型把这三种对象放在同一类型中；检查 role 以后，程序就能识别这一种消息有哪些字段。可以把它理解为“带类别标签的数据”。

toolCalls 是描述请求的普通数据，里面写着工具名、路径和调用 ID。只有宿主程序调用 executeTool，工具才真正执行。第一课的执行器也只是读取内存中的固定内容。

02单步观察循环

先选“读取 README 并回答”，每次点击“下一步”前，预测消息历史会增加什么。尤其观察工具完成之后：文件内容已经存在，但最终回答还没有生成，程序需要再请求一次模型。

下方的“一步”是轨迹中的一个观察点。实验里的 maxSteps 则只计算模型调用次数，两者不是同一个计数。

    再运行两个失败场景

    选择“文件不存在”：第一次工具执行失败，错误被写成一条 tool 消息。模拟模型看见这条错误后，改用正确路径读取。这里没有藏着自动重试逻辑；修正后的读取仍是下一次模型输出的新请求。

    选择“达到模型调用预算”：模拟模型反复要求读同一个文件。两次模型调用和对应工具执行完成后，循环因预算用完而停止。停止不代表任务完成，结果必须保留“预算耗尽”的状态，不能伪装成已经得到答案。

    03谁在推动下一步

    本课把 Agent 分成三个参与者。模型根据消息历史生成回答或工具请求；工具处理一个具体操作；运行时，也就是你要写的宿主程序，负责在两者之间传递数据并控制循环。

    参与者在这个任务里做什么它没有做什么
    模型 model返回“调用 read_file”或最终回答不会因为输出一个工具名，就直接访问文件系统
    执行器 executeTool按指定路径返回内容，或抛出错误不决定要不要再请求模型
    循环 runAgentLoop记录消息、调用工具、检查停止条件不替模型推断文件中的启动命令

    消息历史把分开的调用连起来

    第二次模型调用能知道 README 的内容，是因为程序把工具结果放进了下一次请求。本课每次发送完整历史，因此请求前的顺序应当是：

    user       请读取 README.md，告诉我怎样启动这个项目。
assistant  toolCalls: [{ id: "call-1", name: "read_file", path: "README.md" }]
tool       callId: "call-1", content: "启动命令：npm run dev", isError: false

    id 与 callId 把结果对应到请求。即使只有一个工具，也要保留这个关系。否则增加多个工具调用以后，模型和程序就难以分辨每条结果属于哪一次操作。

    三处容易写错的控制流

    看到文字就结束。 模型可能同时返回解释文字和 toolCalls。本课的结束条件是没有工具请求；“我先读一下文件”显然不是任务已经完成的证据。

    工具失败就丢掉这次调用。 如果不记录失败，下一次模型请求看不见发生了什么。实验把工具异常转为 isError: true 的结果，让模型有机会调整路径。模型调用本身失败则向调用者抛出，不在循环中无限重试。

    到预算上限就留下半次交互。 本课的预算只限制发起模型请求的次数。最后一次允许的请求如果产生了工具调用，仍要执行完这些工具并记录结果，然后停止；否则历史会留下没有结果的请求。

    教学边界

    第一课的模型由固定规则实现，不具备语言理解能力。它让你能够稳定复现一条轨迹，检查循环是否正确；真实模型会不会选对工具、能否完成陌生任务，要在第 3 课接入后另行验证。

    4. 工具结果追加 · agent-loop.ts:283：对照实验中的消息历史，确认结果被放进下一轮使用的上下文。

    第一次读到这四处即可。先能说出“输入 → 循环 → 模型 → 工具 → 历史”的路径，再处理旁边的事件、用户介入和扩展钩子。

    源码中能确认的行为本课如何处理
    pi 从模型响应中筛选 toolCall，再执行工具并追加结果。保留这一控制流，用更小的消息类型练习。
    pi 的循环还检查 steering、follow-up 和显式继续的决定。这些放到后续课；本课没有工具请求就正常结束。
    pi 区分模型错误、中止与输出被截断等情况。本课仅处理工具异常、模型异常和调用预算，不声称覆盖全部情况。
    这里的源码不能支持“pi 自带本课 maxSteps”的说法。maxSteps 是教学实验的显式预算设计。

    以上是静态源码事实与教学简化的对照。关于“为什么这样设计”的讨论是本课的工程分析，除非另列作者原文，不把它归为作者本人动机。

    05亲手补齐循环

    在课程仓库根目录打开终端。你只需实现 labs/01-agent-loop/loop.ts 中的 runAgentLoop。模型、内存文件、命令行入口和轨迹记录已由脚手架提供。

    npm run lab:01:test

    第一次运行会失败，因为关键函数尚未实现。这是练习起点。根据测试反馈补齐函数，再重复运行，直到通过；不要修改测试或用参考实现覆盖自己的代码。

    输入和输出约定

    函数接收 initialMessages、model、executeTool 和 maxSteps。返回值包含 status、messages 与 steps：状态只能是 completed 或 budget，步数是实际模型调用次数。

    • 保留初始消息，不原地修改调用者传入的数组。
    • 每次模型输出先进入历史，再判断是否存在工具请求。
    • 按顺序执行本轮所有工具，成功和失败都写成关联到调用 ID 的结果。
    • 没有工具请求时返回 completed；预算用完而仍需继续时返回 budget。
    • maxSteps = 0 时不调用模型；模型本身抛出的异常交给调用者处理。

    先写自己的版本，卡住再展开提示

    提示 1 · 先找哪些数据需要跨轮次保留

    比较模拟器的第一次和第二次模型请求。消息历史必须继续积累，模型调用计数也必须保留。工具的返回值只要写进历史，就不需要另外维护一份长期结果列表。

    提示 2 · 两种退出路径应放在哪里

    预算检查发生在发起下一次模型请求之前。正常完成检查发生在本轮 assistant 消息写入历史之后。如果仍有工具请求，执行本轮工具，再回到预算检查。

    提示 3 · catch 的范围会改变错误含义

    只把 executeTool 的异常转换成工具错误消息。不要用包住整个循环的 catch，把模型连接错误也包装成某个工具失败；那会把本来不同的失败来源混在一起。

    把终端运行带回网页观察

    06理解本课的取舍

    循环短，并不意味着所有问题都解决了。下面这些约束让第一版容易理解，也限定了它的能力。你要能说明什么时候继续使用它，什么时候增加机制才有价值。

    当前选择解决的问题与收益代价与改变时机
    使用模拟模型每次得到相同轨迹，可以定位循环里的错误，无需费用和凭据。无法验证真实模型的工具选择与任务能力；第 3 课加入真实模型检查。
    串行执行工具执行顺序明确，结果关联和失败反馈容易追踪。相互独立的慢工具会累加等待时间；第 7 课再判断哪些能并行。
    每次发送完整历史模型能看到之前的请求和结果，程序没有额外上下文策略。真实调用的输入会随历史增长；第 9 课处理长度、成本与信息丢失。
    设置模型调用预算阻止反复调用工具的轨迹无限继续。可能截断仍在推进的任务；调用次数也不能直接代表 token 成本或耗时。
    工具异常反馈给模型保留失败证据，允许模型改变下一步操作。反馈不保证恢复；真实工具还需避免把秘密或内部错误详情泄露给模型。

    第一课也没有实现文件写入、任意 shell、权限隔离和持久化。这里的工具只读内存数据，因此可以专注于循环。接入真实副作用之前，必须重新讨论执行边界；不能把教学程序直接当成可安全运行任意命令的 Agent。

    07检查你的理解

    先选择答案，再查看反馈。如果答错，回到模拟器找一条能够证明或反驳答案的轨迹。

    1. assistant 同时返回“我来读文件”和一个 toolCall，循环应该怎样做？

    2. 工具返回“文件不存在”，下一次模型请求为什么必须带上这个结果？

    3. maxSteps 为 1，第一次模型请求返回一个工具调用，本课约定的行为是什么？

    08提交与评审

    完成后，把改动和测试结果交给我，并附上三句话：为什么工具请求也要进入历史；为什么工具执行成功不等于任务完成；你为控制循环增加了什么限制，以及它会错过什么合法任务。

    评审先检查行为是否符合约定，再看错误边界和结构是否清楚。测试通过之后，还需要解释一个变化场景：同一条 assistant 消息提出两个工具请求，其中一个失败时，下一次模型应当看到哪些消息？
