第 02 课 · 从模型意图到可执行操作

模型说要调用工具，
程序还需要检查什么？

上一课假定模型总能返回正确的工具名和路径。这次它请求 read_file({ path: ["README.md"] })。数组当然也是合法 JSON，却不是工具接受的路径。你的任务是在执行之前拒绝它，并把原因关联到这次调用，让模型有机会改正。

先修：第 01 课实验：内存文件，无 API 调用源码基线：1be312b46

一段文本怎样变成一次操作

先写下你的预测：工具名字不存在时，应该抛出并终止整个 Agent，还是反馈给模型？参数合法但文件不存在时，错误又发生在哪一层？如果这两个问题混在一起，日志可能只剩一句“工具失败”，你就无法判断该改提示词、校验器还是文件路径。

assistant: id=c1, name=read_file, arguments={"path":["README.md"]}
执行器:    找到 read_file → 检查 path → 拒绝数组 → 没有读文件
tool:      callId=c1, isError=true, content="Expected exactly { path: non-empty string }"
assistant: id=c2, name=read_file, arguments={"path":"README.md"}

第一条错误是输入协议失败；第二次请求通过校验后，才可能发现文件不存在。把错误放回历史提供了恢复条件，是否更正仍由模型决定。课堂的固定响应会演示更正，但真实模型可能反复犯错，因此第 01 课的循环预算仍然必要。

先预测，再沿调用 ID 观察

选择一个场景，比较 validated、executed 与最终结果。以下是教学模拟，数字不表示实际耗时；终端 demo 会另外执行参考代码。

声明、校验和执行承担不同职责

工具声明告诉模型有哪些操作、参数长什么样。它是请求中的数据，不是权限凭证。运行时校验在收到外部输入后检查类型和约束。业务检查发生在工具内部，例如文件是否存在、替换文本是否唯一。即使模型供应商提供严格输出模式，程序也不应把所有外部请求当作可信内部值。

层次本课检查失败后的行为
响应完整性stopReason === "length"整批不执行，逐调用反馈截断
名称解析恰好一个注册工具与名字匹配未知或重复注册均返回错误
参数协议恰好包含非空字符串 path在 run 之前拒绝
业务操作内存文件确实存在捕获工具异常并保留调用 ID
运行控制是否收到取消信号向外抛出，停止发起新操作

为什么 arguments 使用 unknown

TypeScript 类型只检查你编写的程序。网络收到的 JSON 并不会因为你写了类型注解就自动正确。用 unknown 表示“尚未检查的值”，会迫使你先判断它是不是对象、path 是不是字符串。直接使用类型断言相当于跳过这个问题，不能算校验。

本课没有编写通用 JSON Schema 引擎：工具声明使用 JSON Schema，校验函数逐项检查这个小工具。好处是能看清执行边界；代价是声明与校验两处可能漂移。加新字段时必须同时修改二者与行为测试。工具种类增多后，像 pi 那样使用统一 schema 校验更有价值。

调用 ID 是关联键，不是幂等键

两次 read_file 请求可能读取不同文件，名字不足以关联结果，所以结果必须使用原始 callId。但保留 ID 并不会自动防止重复写文件：如果宿主再次执行同一个调用，副作用仍可能重复。恢复与去重属于第 08 课；本课只拒绝同一响应内重复 ID，避免记录无法消歧。

取消不是普通失败

文件不存在后，模型可以尝试另一个路径；用户已经取消时，再让模型重试就违背了用户意图。因此参考实现捕获工具异常后先检查 signal，再决定是否生成错误消息。取消可以与某个工具异常同时发生，本课优先把取消交给循环处理。已产生的副作用不会因此撤销。

沿 pi 的三层边界阅读

先进入 runLoop 的工具分支：它在调用执行器之前判断输出截断。接着读 failToolCallsFromTruncatedMessage 的注释，理解为什么“参数能解析”仍不足以授权执行。

继续看 prepareToolCall：查找工具、准备参数、统一校验，再运行 beforeToolCall。最后看 runToolCall 如何复用准备、执行与结果处理。这个公共入口能让工具调用另一个工具时仍经过相同钩子，而不是绕过检查。

以上是当前源码可确认的行为。教学程序保留“检查在执行前”和“失败结果可关联”的核心顺序，暂不实现 pi 的参数修复、前后钩子、结构化内容与增量工具输出。取消处理也不同：pi 的工具执行路径可产出中止错误结果；本课向循环抛出取消，由后续运行控制层决定历史怎样收尾。不要把参考解答当作 pi 的缩写副本。

补齐两个决定执行权的函数

打开 exercise.ts。先实现 executeToolCall，再实现 executeResponseTools。参数声明与内存工具已放在 fixtures.ts；测试位于 exercise.test.ts。

npm run lab -- 02 test
npm run lab -- 02 demo
npm run lab -- 02 verify

test 检查你的 TODO；demo 和 verify 明确使用独立参考实现。初次 student 测试失败是预期。先让成功路径通过，再处理未知工具与坏参数，最后增加截断和取消边界。

  1. 返回的每个 ToolMessage 必须有原始 callId；普通异常写成 isError，不要把失败变成空成功。
  2. 验证失败不能进入 run；响应截断不能执行任何调用。
  3. 重复注册名称返回明确错误；同一批重复调用 ID 整批拒绝。
  4. 开始前、执行前及 await 返回后检查取消。捕获异常时仍要允许取消向外传播。
提示 1：先写出信任边界

model 的返回值是意图，工具列表才是宿主允许的能力。先查列表，别用工具名访问 globalThis 或拼接命令。

提示 2：catch 的范围应该多大

捕获查找、校验与工具执行的异常，统一生成反馈。但每次进入 catch，先检查是否取消。执行前的取消检查可以放在 try 外。

提示 3：为什么先处理 length

响应完整性属于整个消息。若在逐个工具执行到一半才判断，前几个工具可能已经写文件，无法做到整批不执行。

这些选择换来了什么

选择收益代价及改变条件
统一错误反馈模型获得更正参数的机会增加轮次，错误文本还可能泄漏内部信息；真实工具应限制反馈内容
显式 validate校验顺序可读，便于观察副作用前的边界schema 与校验可能漂移；工具多时引入受验证的 schema 库
截断整批拒绝避免执行“形状完整、语义残缺”的写入前面原本完整的调用也被放弃；安全性优先于节省一次重发
顺序执行结果关联与副作用顺序容易检查独立慢工具等待累加；第 07 课再引入并发调度

设计推断：先把工具调用当协议，再考虑便利性，可以让恢复、权限和日志共用一个入口。这不是从“极简”二字推导出来的美学偏好，而是因为执行副作用之后再发现输入不合法，通常无法无损回到原状态。

自测与提交

参数是 { path: "" }，JSON 解析成功。应该执行吗？

不执行。语法解析只说明它是合法 JSON，非空字符串是工具自己的参数约束。

两个工具调用都叫 read_file，可以用工具名匹配结果吗？

不能。不同调用可以对应不同路径；结果必须携带各自的调用 ID。名称用于选择实现，ID 用于关联一次操作。

工具抛错时 signal 同时已取消，本课应返回工具错误吗？

取消向外传播。否则循环可能把“用户要求停止”误当成“模型应该修复工具调用”。

提交代码与测试结果，再画出“未知名称、参数非法、文件不存在、响应截断、用户取消”的五条轨迹，标出每条是否执行了工具。评阅重点是执行权在哪一步获得、错误反馈是否足够明确，以及哪些副作用已经无法撤销。
