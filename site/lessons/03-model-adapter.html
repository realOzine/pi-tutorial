第 03 课 · 第一个可切换模型的 MVP

保持循环不变，
让真实模型决定下一步。

前两课中，模型返回值由我们预先写好。现在把同一个接口接到 HTTP 服务：模型真实返回工具调用，宿主执行，再把结果发回去。困难不只是发出一个 POST，而是转换协议时不丢掉调用关联、输出完整性和实际用量。

先修：第 02 课实现：Node fetch + Responses API默认验证：本机 HTTP fixture

先看全局，再进入本课

用图定位本课的职责，再沿箭头观察调用与数据变化。以下是教学示意，不能替代真实运行证据。

“能返回文字”还不是模型接入完成

设服务返回两项：一句“我先读取文件”和一个 function_call。如果适配器只取文字，循环会把它当最终回答结束，文件根本不会被读取。反过来，如果丢掉工具结果的关联 ID，第二次请求可能被服务拒绝，或者模型看不懂这条结果对应哪次请求。

课程循环                 适配器                      模型服务
ModelRequest    →        POST /v1/responses     →     生成输出项
执行 read_file  ←        ModelResponse         ←     function_call(call_id=c1)
追加 ToolMessage →       function_call_output(c1) →  根据文件内容回答

适配器是两种协议之间的转换边界。课程内部关心 user、assistant、tool；Responses API 把函数请求和结果表示为独立项目。先让这条路径正确，再考虑流式、多模态和多供应商，不要一开始就做一个掩盖差异的“万能模型类”。

逐项核对第二次请求

选择成功或输出截断情境。这里是教学数据；实验测试会启动真正的本机 HTTP 服务，检查序列化后的请求，但它不是远程模型，也不产生付费推理。

你要实现的两次转换

本课采用用户指定的 gpt-6.1-terra。官方模型页明确说明工具调用需要 Responses API；本课固定 reasoning.effort: none，保留可理解的文本与函数工具子集。这个事实是 API 约束，不是 pi 的架构选择。官方模型说明核验于 2026-10-30。

课程数据Responses 数据必须保留的含义
systemPromptinstructions每次请求发送当前指令
user.contentinput 中的 user 消息原始任务
assistant.toolCallsfunction_call 项name、JSON arguments、call_id
tool.callId 与 contentfunction_call_output结果对应哪个调用；成功与失败

课程的 isError 在 Responses 函数结果里没有同名专用字段，因此本课把它连同 content 序列化为结果字符串。这样模型可以看见失败，循环仍保留结构化的错误标记。不要只写一句“失败”，然后丢掉是哪一次调用或具体哪个参数出错。

响应解析从 unknown 开始

HTTP 200 的 JSON 仍是外部数据。先确认顶层对象、status 和 output 数组，再按 item.type 分支。文本项目提取 output_text；函数项目检查 call_id、name 和 arguments，解析 JSON 后得到课程 ToolCall。不能把 output[0] 固定当作文字，因为一个响应可能有多个项目。

完整响应中的坏 JSON 参数作为协议错误抛出。若整条响应因输出预算耗尽而 incomplete，允许把残缺参数原文保留为证据，并映射为 length；第 02 课执行器会拒绝整批。本课不会自动“修好”字符串后执行写入。

明确拒绝尚未支持的能力

当前小接口没有推理项、图片、托管工具或多模态内容。适配器遇到这些项目会明确报错，避免悄悄丢掉后续轮次需要的数据。开启推理后可能需要保留 provider 的推理项目；仅改 effort 并不足以扩展当前协议。官方函数调用指南展示了调用与结果的往返，本课按自己的小协议实现这一路径。

把错误分给能够处理它的层

工具错误通常能回给模型更正；鉴权错误不能靠模型换一个文件路径解决。本课不在模型适配器里自动重试，避免超时后再次付费，也便于你看到第一次失败的原因。

情况本课结果下一步由谁决定
HTTP 401 / 429 / 5xx带状态码的异常，不回显原始错误体调用者检查配置、限流或重试策略
网络或 JSON 结构错误异常；不伪造 assistant 回答适配层维护者核对协议和连接
超时TimeoutError用户或运行策略决定是否重新请求
用户取消传播原始取消原因循环停止启动新的工作
输出预算耗尽length → MVP 的 truncated用户检查输出上限与任务是否过大

超时要覆盖 headers 之后的响应体读取。否则服务器先发 headers 再停住，你的超时保护就可能失效。实验专门测试这一条。响应体另设 1 MiB 上限；这是本课程的内存边界，属于教学选择，不是 OpenAI 最大响应大小。

调用数、token 与金额是三个量。maxSteps 限制模型请求次数；max_output_tokens 限制每次生成上限；总费用还取决于输入、缓存和服务计费。usage 缺失时应报告未知，而不是补成零。真实运行要另外保存模型、时间、调用数、结束原因和服务报告用量。

pi 把供应商差异放在哪里

回到 streamAssistantResponse：它先变换上下文，再转换成模型消息，最后调用传入的 streamFunction。循环并不需要知道 HTTP 请求怎么拼接。

再打开 pi 的 openai-responses.ts，沿 stream → buildParams → client.responses.create → processResponsesStream 阅读。这个文件显式设置 store=false，配置输出预算和 reasoning，并把响应处理交给共享流处理函数。它还处理重试、缓存、服务等级、兼容能力和多个登录方式。本课只读取这条装配路径，不声称已经审计整个共享流处理实现。

两者的共同点是把服务协议与 Agent 循环分开。区别也很重要：pi 面向多 provider 和交互终端，使用流式输出及丰富消息类型；本课先用非流式 HTTP，保留最小文本与函数契约。第 05 课再加入增量事件，避免同时学习两套复杂状态。

先过离线协议，再显式运行真实模型

提示 1：先手写一个两轮请求

第二轮应包含原始 user、先前 function_call 和 function_call_output。不要只发送工具结果；不要把输出项 id 当成 call_id。

提示 2：先看全局 status，再处理 output

HTTP 成功与生成完成是两回事。status 为 incomplete 时检查原因；只有输出上限才映射成 length，其他中断不要伪装成正常回答。

提示 3：没有 usage 时为什么报错

当前契约要求 provider 给出用量。如果你选择将来支持缺失 usage，就应该把类型改成“已知 / 未知”，而不是填零来维持现有类型。

真实调用是单独的操作

在本地安全设置 OPENAI_API_KEY，并确认账户预算后，显式执行：

export OPENAI_MODEL=gpt-6.1-terra
node labs/03-model-adapter/demo.ts --live

不要把 API Key 放进网页、源码或 Git。该示例最多请求三次、每次输出上限 256 token，文件工具仍是内存教具。它会输出实际 usage 和停止原因；不会读取你的真实项目。真实调用证据与本地 fixture 检查分开记录。

自测：返回 HTTP 200 后可以立即标记 completed 吗？

不可以。仍要读取响应体，检查 status、输出项与必要字段。生成可能 incomplete，也可能返回格式不受支持的内容。

自测：为什么工具结果的错误标记要进入 output 字符串？

课程内部字段不能自动穿过供应商协议。必须明确映射，否则模型只看到内容，可能把失败文本当作正常结果。

迁移题：换成需要保留推理项的模型，应该改哪里？

先扩展消息与持久化契约，保留 provider 要求的项目，再改输入输出适配；只修改请求的 effort 会破坏后续轮次所需信息。

提交你的映射代码、离线测试输出，以及手画的两轮请求。若跑了真实模型，再附实际用量和失败样本。评阅先检查协议与停止边界，再讨论模型行为；一次成功不证明任务成功率。
