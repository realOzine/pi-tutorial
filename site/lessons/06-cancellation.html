06 / CANCELLATION & INPUT

用户说“停下”，
程序究竟停在哪一步？

工具正在修改文件时，用户可能说“停止”，也可能说“接下来用中文”，或“做完后再总结”。这些话都来自输入框，却要求不同的控制行为。本课把它们的生效时机写成明确协议。

先修：流式事件实现：输入队列与取消传播验证：可控假模型与工具

相同入口，不同承诺

假设模型一次请求了两个工具：先写配置，再检查配置。用户在第一个工具执行时说“别继续了”。你能保证第二个工具不开始，但如果第一个已经写入磁盘，不能靠把 aborted 设为 true 就恢复原文件。

把三类要求分开，才能给出可验证的承诺。取消 abort 通知正在运行的操作尽快结束，并阻止后续工作；引导 steer 在当前轮次完整结束后进入下一次模型请求；追加 followUp 等当前任务本来要停止时才进入。

用户表达本课动作生效点
“停止”触发 AbortController可取消 I/O 收到信号；循环边界检查后不再启动工作。
“后面用中文回答”加入 steering 队列当前 assistant 的全部工具结果已记录之后。
“做完再写一段总结”加入 follow-up 队列没有工具与 steering、当前任务准备结束时。

这些是课程选择的语义。不同产品可以提供不同交互，但不能一边承诺“立即停止”，一边只是把“停止”作为普通文本放到模型下一轮请求里。

把同一条输入放到不同阶段

先预测：读取工具执行期间同时加入 steering 和 follow-up，下一次模型请求应该包含哪一条？再切换到取消场景，数清实际启动的工具。页面是教学模拟，不是对外部进程停止能力的实测。

如果取消发生在模型等待期间，结果会不同：本课直接返回 cancelled，不把尚未完成的 assistant 响应追加进历史。取消发生的位置决定已经产生了什么；“按下了停止”本身不足以说明当前状态。

队列决定时机，信号传递意图

为何不在工具中途插入消息

模型已经发出一条带工具请求的 assistant 消息，下一次请求需要看到关联的工具结果。若随意把用户消息夹在这组尚未完成的交互中，主循环要同时处理工具还在运行、旧请求是否作废、哪些结果仍要接收等问题。先完成整批，再读取 steering，可以保留一个清楚的轮次边界。

本课两条队列都按 FIFO，也就是先到先取，每次只取一条。turn 边界只检查 steering；idle 边界优先 steering，否则取 follow-up。这样“做完以后”的任务不会因为正在运行的模型又请求了工具而抢先进入。

模型响应 → 记录 assistant → 执行本轮工具 → 记录结果
                                              ↓
                                  steering 有消息？→ 下一轮
                                              ↓ 没有
                                    仍有工具链？→ 下一轮
                                              ↓ 没有
                                  follow-up 有消息？→ 下一轮
                                              ↓ 没有
                                           completed

在代码中，工具链是否继续由本轮是否有工具调用决定；示意图中两个判断的先后不改变“工具批次必须先完成”的原则。实验让后续模型请求直接记录它收到的消息，避免只检查队列长度而没有确认输入真的进入请求。

AbortSignal 不会抢占 JavaScript 函数

AbortController.abort() 改变信号状态并通知监听者。模型适配器要把信号传给 HTTP，工具要把它传给可取消操作，循环要在启动下一项工作前检查它。一个完全忽略 signal 的函数仍然会继续运行，直到自行返回或外部进程控制结束它。

这里不能用 Promise.race 让调用方先返回，就宣称工具已经停止。落败的 Promise 不会自动取消；它可能稍后继续写文件。课程实现等待已经开始的调用结算，保留其实际结果，再阻止尚未开始的工作。下一课在并行场景中同样要求收拢已经启动的任务。

取消后如何保持历史可解释

本课为尚未执行的工具补一条关联错误结果，不把它伪装成工具自己失败。这样恢复时能区分“完成了写入”和“检查从未开始”。已经执行成功的工具结果仍保持成功，即使全局状态是 cancelled；局部操作成功与整个任务完成是不同层级的事实。

步骤预算仍然约束所有模型请求，包括 steering 和 follow-up 引起的请求。否则一个不停追加任务的队列可以绕过第一课的预算。预算用尽时保留尚需回答的用户消息，以 budget 返回，不擅自生成“已完成”的结论。

沿 pi 的输入路径读代码

固定源码版本 1be312b46。先看 steer 与 followUp，它们只入队，不调用模型。PendingMessageQueue 支持一次一条或一次全部；本课只保留一次一条，减少策略分支。

然后看 runLoop：入口先读 steering；完成本轮工具并追加结果后再读 steering；没有自然继续条件时才检查 follow-up。当前版本还包括 finishTurn 和显式继续，本课没有复制这些扩展决策。

再沿 abort 到 runWithLifecycle 找到本次运行的 AbortController。控制器属于一次运行，不是所有会话共享的全局开关。模型函数和工具调用接到的是同一条运行取消链。

最后读 continue：它检查当前是否正在运行以及历史末尾角色。一次普通 prompt 也会拒绝与已有运行重叠，而提示调用者排队或等待。这让“当前会话只有一个主循环在修改历史”成为容易推理的约束。

课程选择与源码事实分开

本课返回显式状态，并为本轮取消后未启动的调用补关联错误结果；pi 的细节需看其顺序与并行分支，不能说它在所有取消位置都生成与课程相同的历史。本课以小型模型和工具验证控制机制，没有验证终端、所有 provider 或外部子进程的完整取消能力。

把取消写进调用路径

打开 学生入口。先完成 InputQueue.drain，再补 runControlled。不要让队列负责调模型：队列只决定当前边界能取出哪些数据，循环才决定下一步是否执行。

  1. 用独立测试证明 turn 不取 follow-up，idle 优先 steering，一次只取一条。
  2. 从第一课循环出发，在整批工具完成后读取 steering，在准备停止时读取 follow-up。
  3. 把同一个 signal 传到 model 与 execute，启动前检查；区分取消与普通异常。
  4. 取消时保留已经完成的工具结果，为没有开始的调用写清原因，并返回 cancelled。

提示 1 · catch 应该包住哪一层？

工具异常转换成关联工具结果；模型异常只有在 signal 已取消时转换成 cancelled，否则向上抛出。把整个循环包成“工具失败”会丢掉真正来源。

提示 2 · 取消后能否直接丢掉剩余调用？

本课要求每个已记录调用都有可解释结果。尚未执行的项补 cancelled 错误；不要假装真的调用过工具。

提示 3 · 先判断预算还是先读取队列？

只要不超额调用模型，两种组织可以保留不同的待处理状态。本课把已到边界的输入写入历史，再以 budget 返回，让调用者明确知道还有一条输入尚未回答。按实验契约保持一致即可。

立即反馈不等于立即抢占

设计解决的问题代价
轮次边界注入 steering保持本轮工具交互完整，新的请求上下文明确。慢工具会推迟用户引导；需要界面说明消息已排队。
单独的 follow-up 队列把“改变当前任务”和“增加后续任务”分开。多一份状态与优先级规则；必须考虑长期 steering 导致追加任务等待。
协作取消并等待已启动操作返回时知道哪些操作已经结算，避免后台仍偷偷改文件。不合作的工具会拖延结束；需要工具超时或进程级终止策略。
取消不自动回滚如实保留外部世界已经发生的变化。用户可能需要检查 diff 或执行显式补偿；涉及事务的工具应自行提供撤销能力。

加入更多队列策略之前，先检查真实需求。如果只有单人顺序任务，固定一次一条通常已足够。若要多人协作或分布式任务，就需要重新讨论身份、优先级、持久化与冲突；不能把这个内存数组包装成可靠任务系统。

自测与评阅

工具已经写入文件，随后 signal.aborted 为 true，应该把结果改成失败吗？

不能凭全局取消改写已知事实。记录这次写入成功，同时把整个运行标为 cancelled。若工具在信号到达时结果未知，应明确未知，不能猜测回滚。

follow-up 已排队，但本轮又请求工具，应该现在发给模型吗？

本课继续当前工具链。只有没有工具与 steering、原任务准备停止时，follow-up 才进入请求。

AbortSignal 等同于 Go 的 context 取消吗？

可用于理解“沿调用链通知取消”的思路，但具体 API 和并发模型不同。二者都不能凭通知自动撤销副作用；每个阻塞操作都需要支持取消。

提交学生检查输出，以及两段解释：取消发生在模型等待和首个工具完成后，历史分别是什么；为何一次工具成功不能使整个 cancelled 运行变成 completed。评阅还会把一个工具改成忽略 signal，检查你是否仍会错误宣称它已经停止。

下一课把多个独立工具同时启动。此时取消会影响一批正在运行的任务，完成顺序也不再等于调用顺序。
