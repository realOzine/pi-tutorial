07 / TOOL SCHEDULING

两次读取可以并行，
一次写入会改变什么？

模型同时请求 README 和配置文件时，顺序等待会累加耗时。但“修改配置，再检查配置”不能任意交换。本课用一个简单、可解释的规则选择并行与串行，并把完成顺序和消息顺序分开。

先修：取消与输入队列实现：工具批调度器验证：固定并发场景

先确认依赖，再讨论加速

一次模型响应带来两个调用：read README.md 和 read package.json。如果它们只读取稳定文件，没有共享可变状态，就可以一起等待 I/O。此时顺序执行只是更简单，并没有业务上的必要。

换成 edit config.json 与 check config.json，检查必须看到修改后的内容。一起启动可能让检查先读到旧文件；即使最终两项都返回成功，也不证明任务按预期验证了新配置。调度正确性来自依赖约束，不能根据工具名称里有没有“read”简单猜测。

本课采用 pi 当前的一条易理解规则：默认整批并行；只要任何调用对应的工具声明 sequential，整批按调用顺序串行。它保守地处理“有一项需要独占”的情况，不构造复杂的依赖图。

独立读取：read A ─────┐
          read B ──┐  ├→ 全部结果 → 下一次模型请求
                   └──┘

有序操作：edit A → check A → 全部结果 → 下一次模型请求

先手写结果：模型调用顺序 A、B，B 先完成，页面应该先显示谁？下一次模型请求中的工具结果又应该怎么排？本课的答案是：完成事件先 B 后 A，最终结果数组保持 A、B。

完成顺序与返回顺序各有用途

单步切换下面两个场景。模拟中的快慢只是用来说明时序，不是性能测量。注意串行场景中，即使 read 本身允许并行，也受整批规则影响。

加入取消再预测：并行模式下 A、B 已经启动，A 触发了 abort。你不能从数组里删掉 B 就认为它消失了；它必须收到信号并结算。测试将确认调度器返回时，两项的清理都已经完成。

把决定与执行分开

预检不产生工具副作用

调度器先按调用顺序查找工具、校验参数，保存可执行项或立即错误。未知工具、参数错误不会进入 execute；合法项仍然可以继续。本课预检不是全批事务：一个调用不合法不会自动禁止其他合法读取。

在预检完成前不启动任何获准调用，便于加入统一的决策边界。但校验通过不等于取得操作系统权限，也不保证状态永远不变；工具执行时仍须落实路径、权限和业务条件。第 02 课执行器被独立使用时也必须校验，所以组合后可能校验两次；validate 应保持纯检查，不写文件、不扣预算、不改变共享状态。

Promise.all 不决定是否并发

真正启动工作的时刻是调用异步函数，而不是写下 Promise.all 的时刻。先在循环里逐个 await execute()，最后再 Promise.all，工作已经串行完成。要重叠，就先为获准项创建进行中的 Promise，再等待这批结果。

Promise 的结果数组会按输入位置排列，即使后面的任务先完成。本课利用这个性质保留模型调用顺序，另用 onResult 及时通知界面。调用 ID 仍是关联依据；数组顺序只是一种稳定、容易复查的记录约定，不能代替 ID。

失败分为工具失败与观察者失败

工具抛错会转换为对应的 ToolMessage，其他工具仍可以成功。监听器抛错则意味着执行过程的观察或记录发生问题，本课向调用方抛出；但并行分支先用 Promise.allSettled 等所有已启动操作结算，再传播该错误。否则一个慢写入可能在运行器已经返回后继续修改文件。

这并不提供事务回滚。观察者失败前，一些工具已经产生副作用；调用者必须保留能够获得的证据并决定如何恢复。第 08 课要引入持久日志，正是因为“有一个 Promise 失败了”不足以说明外部世界处于哪种状态。

取消不会使已启动 Promise 自动消失

在每个 execute 之前再次检查 signal，防止预检后、实际启动前发生的取消被忽略。顺序模式中，未开始项只生成关联错误。并行模式中，已经开始的项共享取消信号，并全部结算后返回；一个不合作的工具仍会拖延结束。这是工具契约的要求，不是调度器能凭数组操作解决的问题。

核对 pi 的批处理规则

固定版本 1be312b46 的 executeToolCalls 检查两处：全局是否要求 sequential，以及本轮是否包含声明 sequential 的工具。满足任意一项就走顺序分支，否则走并行分支。Agent 构造配置给出的默认值是 parallel。

在 顺序分支里，每项准备、执行、结束后才进入下一项。并行分支先逐项预检，把获准执行保留为待调用函数，再同时执行；每个函数完成后发送结束事件，最终工具结果消息按原位置发出。

继续读 prepareToolCall，找出参数校验、before hook、取消检查各在哪里。再看 executePreparedToolCall 如何等待工具产生的更新事件，以及如何保存错误。这能帮助你解释“工具结束”究竟包含哪些工作。

本课并非逐行复制 pi

pi 有前后工具 hook、部分输出、提前结束提示和更丰富的错误消息；本课只保留批策略、预检、取消与结果顺序。课程的 allSettled 用于明确等待观察者错误下的已启动任务，不声称 pi 的整个事件错误路径与本课完全相同。以上源码结论来自静态阅读，不是性能评测。

提示 1 · 为什么不要完成一个就 push 一个结果？

并行模式下 push 的顺序是完成顺序。如果要保持原顺序，可保留调用的 index，或等待按原调用顺序创建的一组 Promise。界面事件可以先发，不要求最终数组也乱序。

提示 2 · catch 包住 execute 还是连 onResult 一起？

把 onResult 失败包装为工具失败，会抹掉“工具成功但记录失败”的区别。本课工具异常成为反馈，观察者异常单独传播。

提示 3 · 为何要在预检后再次看取消状态？

预检与执行之间仍有时序边界。即使参数合法，用户已经取消也不应再启动工具；合法性不等于当前仍有执行意图。

一条保守规则能走多远

选择收益代价与替换时机
默认并行独立 I/O 可以重叠。同时占用更多资源；工具作者必须如实声明共享状态约束。
任一 sequential 导致整批串行规则简单，不需要推断文件依赖或建立锁图。一个写入会连带降低无关读取的并发；真实瓶颈出现后才考虑分组或依赖图。
预检集中完成可观察决策与执行分界，坏参数不会启动工具。预检耗时会推迟整批开始；执行时仍要检查变化中的条件。
等待全部已启动项返回时不会留下仍执行中的已知调用。尾部最慢任务决定完成时间；取消不合作时需要工具层超时。
事件乱序、历史稳定界面及时，模型上下文和排查顺序可复现。维护两种顺序，记录时必须保留调用 ID。

本课没有并发上限。模型一次返回少量调用时，整批并行足够清楚；如果实际任务产生数百个调用，应加入资源预算或并发池，并用真实瓶颈验证收益。不要仅因为“以后可能很大”就提前让最小 Agent 背上调度框架。

把文件路径当作依赖键也不是免费改进：别名、符号链接、工具内部访问和外部服务都会使依赖难以穷尽。保守声明有时损失吞吐，却比错误的自动推断更容易解释和测试。

自测与评阅

模型调用顺序 A、B，B 先结束，谁的结果先进入返回数组？

返回数组仍为 A、B；完成事件可以 B、A。对应关系以 callId 为准，不能只依赖数组位置。

一个并行工具失败，可以立刻返回整个批次失败吗？

本课把工具失败保留为反馈，并等待其他已启动操作。立即返回可能留下后台副作用，也会丢失已完成的成功结果。

validate 校验成功，是否证明并行写入同一文件安全？

没有。参数形状合法不能证明执行独立。工具的 execution 声明与真实副作用约束必须一致，必要时串行或用更强的事务机制。
