08 / 会话与恢复

恢复对话，不等于重放操作

Agent 已经把文件改好了，随后在写入“修改成功”之前退出。重启时只看到工具请求，没有工具结果。再执行一次可能重复修改；假定成功又可能把失败说成完成。本课先保存已知事实，再明确保留未知。

先修：第 07 课实验：真实本地 JSONL 文件不调用模型

先看全局，再进入本课

用图定位本课的职责，再沿箭头观察调用与数据变化。以下是教学示意，不能替代真实运行证据。

先区分三个问题

会话日志回答“运行时记录过什么”；投影回答“这次给模型看什么”；工具执行器回答“现在要对外部世界做什么”。这三者有关联，但不能合成一个“恢复”按钮后就忽略差异。读日志如果直接触发工具，打开历史页面都可能再次改文件。

1. 追加 assistant：edit("version = 1", "version = 2")
2. edit 修改磁盘文件
3. 追加 tool：修改成功
                  ↑ 若在 2 和 3 之间退出，日志缺少结果

先预测：重开时能否判断第 2 步已经完成？仅凭这份日志不能。它也可能在第 1 步之后、第 2 步之前退出。这两个外部状态，对日志而言完全相同。因此本课把这类调用标成 needs_review，要求检查实际文件，再由操作者决定补记、放弃或明确重试。

这是恢复语义，不是异常提示的措辞。只要文件修改和日志追加没有共同事务，“先记请求、后记结果”就留有不确定窗口。调用 ID 能关联消息，不能自动保证副作用只发生一次。

JSONL 为什么适合第一版

JSONL 是每行一个 JSON 对象的文本格式。追加一条消息不必重写整个历史；终端也能逐行观察。代价是读文件时要处理不完整尾行、版本与 ID 关联。这里不把它当数据库：单个进程拥有一个日志，多个进程不能同时打开写入。

{"version":1,"id":"u","parentId":null,"message":{"role":"user","content":"检查项目"}}
{"version":1,"id":"a","parentId":"u","message":{"role":"assistant","content":"完成","toolCalls":[]}}

id 标识一条记录；parentId 表示它接在哪条记录之后。按文件顺序直接拼消息会混入其他分支。正确投影先找到选定叶节点，沿父链回到根，再反转为时间顺序。索引是按 ID 查找的映射，构建一次后每一步查找不需要扫描整个数组。

为什么不能把缺结果的请求直接删掉

从发送给模型的上下文中暂时排除残缺交互，目的是满足消息协议；从原日志中删除它，则会失去“可能发生过修改”的证据。本课同时返回安全消息和 pending。一批工具只完成部分时，已完成结果仍保留在原日志；整个批次暂不进入模型历史，缺失的调用列为待核对。

投影也拒绝孤立结果、重复结果、缺失父节点和父链循环。类型检查只能约束编写程序时的对象；磁盘 JSON 是另一个输入边界，需要验证数据形状。记录格式合法之后，还要验证结果是否对应当前未完成请求。

半行与中间坏行采取不同处理

本课规定换行才代表完整记录。没有换行的尾部可能是中断写入，通过 recoverSession(source, newPath) 将之前的完整记录复制到新文件；原文件保留，目标已存在就拒绝覆盖。中间有一条完整但损坏的行，则直接报错。跳过它可能让后面的父节点或工具关联失真，不能悄悄恢复成“看起来正常”的历史。

pi 的会话调用路径

以下是固定版本 1be312b46 的静态源码事实；本课没有运行 pi 的恢复测试。先读数据路径，再对比教学程序的不同策略。

  1. SessionManager.appendMessage 建立 ID、父节点、时间戳，交给 _appendEntry。
  2. _persist 与追加失败处理：首次有用户或助手消息时写文件，之后追加；失败会恢复相应的内存索引与叶节点。
  3. branch 移动叶节点；旧记录仍在文件中。
  4. buildSessionProjection 组合当前路径、压缩边界与上下文编辑；buildSessionContext 提取最终消息。不是所有日志记录都会进入模型请求。
  5. loadEntriesFromFile 逐块读取，跳过无法解析的行，验证头部后处理尾部换行。与本课“中间坏行报错、恢复到新文件”的约定不同。

工程分析：追加树让探索其他回答无需丢弃旧路径；代价是每次读取要明确“所有记录”和“当前上下文”的差别。这个机制不是文件系统版本控制；切换消息分支不会自动把工作目录恢复到当时状态。

DeepSeek Harness 的架构也区分持久会话事件与实时 UI 事件，模型历史由日志投影得到。第 10 课以固定 commit f3803c9 比较插件职责；此处使用其官方架构文档说明这条概念边界，不声称两个项目提供相同的崩溃恢复保证。

写出分支投影

打开 学生入口。磁盘读写脚手架已提供，你实现 projectSession(entries, leafId)。函数只做投影，绝不执行工具。

npm run lab -- 08 test
npm run lab -- 08 verify
npm run lab -- 08 demo

test 检查学生函数，初始 TODO 应失败；verify 检查独立参考答案；demo 实际写入并重开临时日志。三者没有模型费用。测试中的日志 I/O 检查运行已提供的脚手架，其通过不能代替学生投影通过。

  • 空叶节点返回空历史；未知 ID 和循环父链报错。
  • 选定路径里，每个工具结果只能消耗一个已有调用 ID。
  • 当前批次全部完成才进入完整模型历史；否则返回 needs_review 和缺失调用。
  • 保持输入记录不变，保留旧分支；不得把未完成请求自动重试。
提示 1 · 先手画四条记录

令 u 的父节点为空，a 与 b 的父节点均为 u，t 的父节点为 a。从 t 回溯只能得到 u、a、t。数组中 b 的位置不应该改变结果。

提示 2 · 用集合检查哪些结果还没来

读到 assistant 时登记本批调用。读到 tool 时必须找到并移除对应 ID。最后集合不空时，从本批 assistant 开始的消息都暂不提交给模型。

提示 3 · 不确定性要体现在返回值

不要返回“已恢复成功”同时偷偷删掉调用。让调用方必须检查 status，pending 保存仍未知的请求。第 12 课将在这里暂停 CLI 恢复。

比较答案时打开 独立参考实现；重点看它为何先写盘再更新内存，以及发生 I/O 错误后为什么拒绝继续写入。

持久化承诺要说到具体故障

选择收益代价或未覆盖边界
追加 JSONL，而不是重写数组保留路径与原始证据，容易检查每次新增记录。需要版本、父链和损坏处理；加载时间随日志增长。
单进程、同步写入并 fsync 文件在这个小实验里写入次序明确，返回前请求刷新文件内容。阻塞事件循环；没有跨进程锁，也没有把新目录项或外部副作用纳入事务。
未知结果交给人工核对避免盲目重复修改，保留真实的不确定性。恢复不能全自动。若需要自动化，要设计幂等操作、外部事务或可核对的业务标识。
分支只改变消息路径可以比较不同方案，旧讨论仍可查阅。磁盘代码不随消息回滚，需要 Git 或独立工作目录管理。

“恰好执行一次”是对外部效果的承诺，不能从“每个调用都有唯一 ID”推出。若工具是向远端付款，必须由远端支持幂等键或事务核对；把调用 ID 写进本地日志并不能补出这种能力。本课只在本地文件示例上讨论机制。

自测与提交评阅

日志最后一条是 edit 请求。为什么不直接重试？

工具可能已经修改文件，只是结果尚未写入日志。应先检查外部状态；自动重试会把“结果未知”错误地当作“操作未发生”。

文件中共有 10 条消息，当前分支只有 6 条。发给模型几条？

从当前叶节点沿父链选择，再执行工具配对和上下文策略。10 是原始记录数量，不是模型上下文数量；6 条中若有未完成工具批次，还不能全部发送。

branch 后立即退出，能保证重开仍在该位置吗？

本课不能。branch 只改内存叶节点，只有下一次 append 的 parentId 把选择写进日志。若产品需要持久保存光标位置，就应增加明确记录或元数据，而不是在文档中暗示已有。

提交学生实现、测试结果，以及三个退出位置的预期：工具执行前、工具执行后但结果未保存、结果保存后。每个位置分别写清“知道什么”“不知道什么”“恢复能做什么”。再解释中间坏行和尾部半行为什么采用不同策略。
