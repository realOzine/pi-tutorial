09 / 上下文管理

省下的上下文，可能正是下一步的条件

用户第一句说“必须保留端口 8080”。随后工具返回几千行日志，最后用户问“现在应该使用哪个端口？”只保留最新消息很省空间，却把答案的依据删掉了。本课用同一份历史比较全量、裁剪与摘要，观察省了什么，又丢了什么。

先修：第 08 课实验：确定性上下文变换字符预算，不冒充 token 计量

模型窗口是输入限制，也是选择问题

第 08 课的日志可以一直追加，模型的一次请求却不能无限增长。请求不仅包括历史，还包括系统提示、工具声明、检索内容，通常还要给输出留下空间。因此“磁盘存得下”不能推出“下一次模型调用发得出去”。

先把问题缩小到一个可检查的条件：在 300 个序列化字符的教学预算内，如何保留“端口必须是 8080”？全量历史保留证据但超预算；裁剪最近轮次符合预算但失去约束；摘要可能两者兼顾，也可能漏掉数字。我们要分别检查长度与信息，不能拿长度变短当成质量变好。

原始记录：约束 8080 → 大段日志 → 已记录 → 用户追问端口
全量视图：约束 8080 → 大段日志 → 已记录 → 用户追问端口
裁剪视图：                                  用户追问端口
摘要视图：摘要「必须保留 8080」          → 用户追问端口

预测：若摘要写成“用户要求保持兼容”，程序会报告什么？它可能符合长度和格式检查，却没有保存端口。语义遗漏需要针对任务的判定；第 11 课会把这个问题变成固定评测案例。

先观察长度，再检查依赖

这是教学状态模拟，数值用于说明预算，不是实际 token 或耗时。终端 demo 会用真实 JavaScript 序列化长度比较同一份固定历史。

先定义可发送的历史，再决定删多少

整轮保留是一条明确的教学规则

本课把一个 user 消息及到下一个 user 消息之前的所有 assistant、tool 消息视为一轮。裁剪从最新轮次向前增加，直到再加一轮就超预算。这样不会把工具请求和结果拆开；同时承认代价：若一轮特别长，这个简单策略无法继续缩小。

在删消息之前，先校验输入中的工具关联。否则一个原本孤立的工具结果，可能因为恰好被裁掉而“通过检查”，把上游错误藏起来。当前上下文必须是第 08 课投影得到的完整消息，不包括待人工核对的残缺调用。

预算单位必须能复查

实验使用 JSON.stringify(messages).length，它计算 JavaScript UTF-16 代码单元，连 JSON 的键名和括号都算进去。这让测试不依赖某个 tokenizer，但不能拿来计算 API 费用，也不能保证真实模型的窗口上限。英文、中文、emoji 与不同 provider 的编码差异都使“一个字符等于一个 token”不成立。

真实接入时要保留 provider 返回的 usage，并为完整请求的系统提示、工具声明和输出预留预算。我们的函数只处理历史消息视图。返回 ready 表示满足本课约定，不表示整个 HTTP 请求已通过 provider 的限制。

摘要是派生材料，原始证据不能被覆盖

摘要器接收较早的完整轮次，返回文本。本课将文本明确标为历史摘要，放在最近轮次之前，并保存 sourceIndexes。这些索引相对于本次输入；接到会话日志后，应映射到稳定记录 ID，这样以后裁剪或分支时还找得到原文。

摘要器失败时，函数返回 summary_failed 和未改变的原历史。摘要生成成功但仍超预算，返回 over_budget。调用方只有拿到 ready 才能发送请求。取消信号保持为取消异常，不伪装成一个可继续使用的摘要结果。

“有来源”也不等于“忠于来源”。摘要可能把否定句改成肯定句、漏掉版本号或把未完成工作写成已完成。必须用任务中的关键问题检验它；若问题需要精确数值，保留原始短证据往往比再概括一句更稳妥。

pi 把压缩拆成准备、生成与会话投影

固定版本 1be312b46 的 compaction.ts 与上一课的会话管理文件均已完整静态阅读。下列路径解释实际控制流，未把这些源码当作本课程已经运行过的性能实验。

  1. estimateContextTokens 优先利用最近的有效 usage，再估算后续消息；投影估算还考虑后续编辑或压缩会使旧 usage 失去代表性。
  2. shouldCompact 根据窗口与预留量判断触发；这与我们的硬字符上限是不同策略。
  3. findCutPoint展示切分边界；prepareCompaction使用投影后的消息寻找边界，准备较早历史与可能被切开的轮次前缀。
  4. compact生成摘要，需要时分别处理较早历史与当前轮次前缀，再合成结果。
  5. getSummarizationFailure拒绝错误或达到输出上限的不完整摘要；后续逻辑也拒绝摘要响应中的工具调用。
  6. 会话追加压缩条目后，新的模型投影使用摘要与保留区间；旧原始条目不因压缩而删除。

教学简化：pi 能在合法边界切开一轮，并对该轮前缀生成额外摘要；本课先保留整轮，减少需要同时推理的状态。工程取舍是实现和测试更清楚，但超长单轮必须停止或另设策略。源码中的字符启发式估算也不应被当作所有语言、所有 provider 上的计量保证。

Anthropic 的上下文工程文章讨论了摘要与按需读取的用途。这里把它作为策略来源；是否改善你自己的任务，要由同任务、同模型配置的比较实验验证。

初始八项学生检查均因 TODO 失败。独立参考实现通过只证明课程脚手架可用。demo 的摘要器按规则复制首条约束，它是透明的教学替身，不具备通用摘要能力，也没有真实模型费用。

  • full：保留原消息并报告长度与是否超预算。
  • trim：只移除完整旧轮次，返回保留与省略的输入索引。
  • summary：全量超预算时才请求摘要；来源范围与最近轮次明确分开。
  • 失败、空摘要、超长摘要、取消分别有可解释结果；输入数组始终保持不变。
提示 1 · 不要先从数组尾部数 N 条

先找所有 user 消息的起点。后一个起点以前是前一轮的完整范围。每次用候选的整个后缀计算预算，最少也要保留最新轮次。

提示 2 · “够短”应该在哪一步检查

原历史先检查；裁剪后的候选再检查；摘要组合后还要再检查一次。摘要器接收预算并不保证返回内容一定满足预算。

提示 3 · 错误分支也要返回证据

摘要失败时不要把原数组替换成空数组，也不要把“摘要失败”当作历史摘要送给模型。保留原历史和明确状态，让调用者停止或选择其他策略。

完成后对照 参考实现。再添加一条“不能改数据库格式”的条件，观察只复制首条约束的固定摘要器会漏掉什么。这个新增反例应进入你的评阅材料。

什么时候换策略

策略适合的约束主要代价
发送全部历史任务短、窗口足够，先建立最容易解释的基线。请求增长，成本与延迟可能上升；更多内容也不保证更容易找到关键信息。
裁剪完整旧轮次旧信息明确无关，当前任务相对独立。跨轮约束可能消失。需要测试证据问题，不能只看协议合法。
保留摘要与来源旧任务状态需要继续，但大量原输出已冗余。额外调用与延迟，内容有损；摘要失败需要回退或停止。
按需读取原文能用路径、ID 或查询定位具体证据。增加工具往返，模型可能找错位置；索引质量与更新也要维护。

这里没有直接引入 embedding。只有当路径、关键词和结构化索引无法找回需要的材料时，才值得用具体失败集比较语义检索。任何检索方案仍要把返回内容接回来源，不能用“相似”替代“支持结论”。

自测与评阅

ready 是否意味着真实 HTTP 请求一定不会超模型窗口？

不能。它只验证本课序列化字符预算。真实请求还包含系统提示、工具声明、provider 格式与输出预留，而且 token 化方式不同。

为什么不能保留最后一条 tool，删掉前面的 assistant？

tool 结果靠 callId 关联 assistant 请求。拆掉请求后，provider 可能拒绝历史，模型也失去了结果对应的动作。

摘要失败时回退原历史，是否应该立即照常发模型？

不能。原历史可能仍超预算。函数返回原历史是保护证据，不是批准发送；调用者必须检查 status。

提交代码、八项测试输出和三种策略的实际结果。说明旧约束何时消失、摘要从哪些索引产生，以及当前轮次太长时为什么选择明确停止。再设计一个格式检查通过、语义却错误的摘要作为反例。
