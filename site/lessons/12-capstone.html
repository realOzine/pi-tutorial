一个正常循环，为什么仍然不够

第 01 课把工具结果加回消息列表，便能开始下一轮。但消息只在内存里：终端关闭后，你不知道上一次执行到哪里。现在假设 edit_file 已经把文件改好，进程却在写入工具结果之前退出。重新执行编辑可能报“旧文本不存在”；对付款或发布操作，这种重复的后果会更严重。

本课不宣称“恰好执行一次”。我们保存请求和结果之间的差别：有请求、没有结果，表示执行结果未知。恢复时停止自动运行，要求核对实际文件。这个选择让人多处理一次异常，却避免把一次不确定的写入当成从未发生。

正常：请求已落盘 → 修改文件 → 结果已落盘 → 下轮检查
中断：请求已落盘 → 修改文件 → 进程退出
恢复：发现没有完整结果 → needs_review → 不自动重复修改

“停止后再继续”与“任意崩溃后自动恢复所有副作用”是不同目标。我们的正常演示验证前者；失败测试验证遇到后者时会拒绝猜测。

CLI 日志、密钥在 workspace 外；语法检查不执行目标程序。

这些模块在同一个 Node 进程里，通过函数调用连接。只有模型请求跨网络，语法检查启动子进程，日志和编辑访问文件系统。Model 接口不是额外的服务；它只是把请求和响应转换成统一类型的函数。

一次请求的先后顺序

  1. 从日志投影当前分支。如果有未配对的工具请求，先停止；不能用新任务盖住未知状态。
  2. 扩展生成本次请求视图，上下文策略决定保留哪些完整轮次。原始日志保持不变；预算不足不发请求。
  3. 调用模型。流式预览只供显示；完整响应才进入持久消息。
  4. 先保存 assistant 的工具请求，再执行整个批次。普通工具错误作为结果返回；取消向外传播。
  5. 批次完成后按请求顺序保存结果，接收一条 steering；没有待执行工具或 steering 时再取 follow-up。
  6. 没有后续工作便完成。调用次数用完返回 budget，保留足够的信息供下一次启动继续。

打开 参考循环，把每个 await 放回这条路径。特别检查：request 观察者取消之后是否还会调用模型？工具监听器失败时，日志能否证明该工具完成？哪些错误应反馈给模型，哪些必须结束本次运行？

作为对照，pi 的 createAgentSession 组合模型、工具、资源、Agent 和 AgentSession；Agent 管理运行状态；agent-loop 处理模型与工具轮次。我们学习的是这些职责之间的关系，没有照搬完整 SDK、UI 与 provider 集合。

第一次应该得到 budget，第二次得到 completed。两个命令启动两个进程，不能靠上一进程的内存传递状态。默认固定规则模型仅用于预设的语法修复任务，不理解开放指令。删除 --reference 会运行你的实现。实验目录已存在时，换一个新名字；--init 拒绝覆盖。

真实流式 API：明确开启才产生费用

使用新的实验目录，添加 --live --key-file secret --steps 6。CLI 固定模型 gpt-6.1-terra；密钥必须位于工具 workspace 外。它调用第 05 课的真实 SSE 适配，并以点号表示收到增量预览。每个请求最多 512 输出 tokens、24 KB 序列化输入，30 秒超时，最多 8 次请求，无自动重试。请先读 运行说明。

每次运行写一个独立 *.run.json，记录请求开始、完成、usage 与预览次数。失败时费用标记为未知；工作量限制不等于供应商账单的硬美元上限。课程仓库不保存密钥，浏览器也不会读取密钥。

用第 11 课评测自己的循环

运行 node labs/12-capstone/evaluate.ts，比较 1 次调用预算与 6 次调用预算；任务集同时包含正常修复、模型只声称成功，以及工具失败。评测使用真实临时文件和固定规则模型，每个任务都有独立判定。更高完成率不能替代更高任务通过率；失败用例的用途是暴露这种差别。

这套实现付出了哪些代价

决定解决的问题代价与升级条件
先保存请求，再执行副作用恢复时知道存在未解决的操作未知状态需要人工核对；若业务支持幂等键，可进一步设计自动恢复协议
整批完成后按请求顺序保存结果协议顺序稳定，模型不看半批结果中途取消会保守地把已完成但未落盘的结果也视为未知；要缩小范围可逐项持久化并保持配对投影
单进程追加日志代码与恢复路径容易检查不支持多进程同时写；并发写入需要锁或独立存储事务
严格小文件工具与固定语法检查结果可复现，权限与输出容易说明不能运行大型构建、任意 shell 或验证业务；扩展能力需要重新审视进程和文件权限
完整原始日志、裁剪请求视图节省请求上下文且可追溯模型可能看不到历史约束；应通过明确任务和评测决定裁剪策略，而非只看 token 变少
可信的静态扩展不改循环也能添加工具与 hook扩展拥有 Node 进程权限；注册接口不是插件隔离机制

本课没有实现完整 TUI、操作系统隔离、多供应商兼容或分布式执行。这些能力会引入新的状态和故障点。先能用失败轨迹说明当前承诺，再决定下一项能力需要什么边界。

用同一个问题比较不同架构

课程固定 pi commit 为 1be312b46abe45d3914743a4d7837ebaf534d390。mini-SWE-agent 和 DeepSeek Harness 也使用固定源码快照。以下是调用路径与状态位置的对照，不是性能排名；这些项目的任务、环境和扩展目标不同。

项目已核实的组织方式从中理解的取舍
piAgent / agent-loop 管运行；coding-agent 的 SDK 与会话层组合工具、资源和持久状态多个宿主可复用循环，但必须明确上下文转换、事件与工具执行的契约
mini-SWE-agentDefaultAgent 的 step → query → execute_actions；actions 按顺序交给 environment，轨迹保存为 JSON 快照路径短，便于观察基线；环境边界承担执行策略，快照与追加树日志的恢复模型不同
DeepSeek Harnessagent-loop 插件通过 Cordis 的 context、服务、事件和生命周期连接模型与工具插件可重组运行机制；理解一次请求需要追踪服务与事件关系，不能只读一个 while

打开 mini-SWE-agent 固定循环快照：query 在下一次调用前检查 step/cost 限制，但成本要在模型响应后才知道，所以不能把 cost_limit 当成严格不超额的预付费闸门。execute_actions 顺序调用环境；完整轨迹通过 save 保存。工具和本地环境的进一步对照见 第 04 课。

打开 DeepSeek agent-loop 固定快照，按 第 10 课的对照追踪生命周期。这里的“简洁”不能只数循环行数：需要同时计算插件注册、状态存储、环境执行与 provider 映射承担了多少工作。课程把这些职责逐步加回去，正是为了看清省略了什么。

毕业验收：实现与解释都要有证据

  1. 运行。展示从读取、唯一编辑、真实语法检查到回答的轨迹；说明判定程序检验了什么、没检验什么。
  2. 恢复。在编辑结果落盘后退出，从新进程继续；再构造只有请求、没有结果的日志，证明它不会重放。
  3. 控制。证明取消、上下文不足、调用预算和截断分别在哪一层停止，是否仍可能已有副作用。
  4. 扩展。启用与禁用项目扩展，说明变化发生在注册表、请求视图还是循环本身。
  5. 比较。选择 pi 与另一个项目的一项设计差异，给出固定源码位置、解决的问题、代价及适用条件。
提示 1：先找不能交换位置的两步

请求落盘与工具执行不能交换；完整响应提交与流式预览不能混用。拿这两组先写一条失败轨迹，再实现正常循环。

提示 2：不要把恢复写成重跑原任务

恢复读取的是完整消息投影。已有工具结果就是下一次模型请求的输入；只有缺失结果时才进入 needs_review。完成的对话没有新输入时，应直接返回。

评阅标准

通过测试只占实现证据的一部分。还要能区分控制流结束、工具调用成功、文件满足要求、业务功能正确四个判断；能解释未持久化副作用的不确定性；能用具体失败案例说明你为什么保留或改变某项设计。为了更短而删掉这些边界，不算完成课程。
